## Phase 1: Security & Privacy Hardening (Immediate P0)

**Goal:** Eliminate student PII data leaks and enforce strict multi-tenant boundaries at the database layer.

1. **Remediate Open User Read Rule in Firestore**
   - **Problem:** `match /users/{userId} { allow read: if true; }` allows unauthenticated access to the entire user directory across all colleges.
   - **Action:** Update [firestore.rules](file:///c:/Users/lenovo_samxiao/Downloads/better-cse-aiml/better-cse-aiml/firestore.rules) to:
     - Require authentication: `request.auth != null`.
     - Allow students to read/write only their own document (`request.auth.uid == userId`).
     - Allow Admins/SuperAdmins to read users matching their `tenantId` or platform scope.
2. **Eliminate Global Unfiltered Snapshot in Client**
   - **Problem:** In [src/App.tsx](file:///c:/Users/lenovo_samxiao/Downloads/better-cse-aiml/better-cse-aiml/src/App.tsx#L514), `onSnapshot(collection(db, 'users'))` downloads all users into client memory.
   - **Action:** Scope queries by `where('tenantId', '==', currentTenantId)` and move user list subscriptions exclusively into [AdminPanelView.tsx](file:///c:/Users/lenovo_samxiao/Downloads/better-cse-aiml/better-cse-aiml/src/components/AdminPanelView.tsx) with pagination limits (`limit(50)`), preventing non-admin clients from fetching directory data.
3. **Database-Level RBAC for Associates & Coordinators**
   - Enforce specific `associatePowers` (`canScanAttendance`, `canCreateEvents`) inside [firestore.rules](file:///c:/Users/lenovo_samxiao/Downloads/better-cse-aiml/better-cse-aiml/firestore.rules) rather than relying exclusively on frontend UI button hiding.

## Phase 2: Architectural Modularization & Data Access Refactoring

**Goal:** Decompose the 3,132-line monolithic [src/firebase.ts](file:///c:/Users/lenovo_samxiao/Downloads/better-cse-aiml/better-cse-aiml/src/firebase.ts) into domain services.

1. **Modularize the Services Layer**
   - Split `src/firebase.ts` into isolated modules:
     - `src/services/auth.service.ts`: Firebase Auth, synthetic email mappings, password updates.
     - `src/services/events.service.ts`: Event CRUD, capacity checks, transactions.
     - `src/services/registrations.service.ts`: Solo/team registrations, passes, attendance check-ins.
     - `src/services/certificates.service.ts`: Template rendering, batch creation, verification lookups.
     - `src/services/vault.service.ts`: Cascade soft-deletes and recovery restores.
2. **Unified State Management & Query Caching**
   - Replace redundant real-time snapshot listeners with dedicated hooks (`useTenantEvents`, `useUserRegistrations`) to prevent duplicate Firestore reads on tab switches.

## Phase 3: Media & Authentication Infrastructure Upgrade

**Goal:** Secure image uploads and streamline collegiate user identity.

1. **Secure Cloudinary Media Ingestion**
   - **Problem:** The unsigned preset (`notx_preset`) allows unauthenticated file uploads to Cloudinary storage.
   - **Action:** Transition to signed uploads using an ephemeral token endpoint (e.g., lightweight Firebase Cloud Function or Cloudflare Worker) or restrict preset IP/domain origins in the Cloudinary dashboard.
   - Implement automatic Cloudinary asset deletion when an album or banner is permanently purged from the recovery vault.
2. **Normalize Identity & Password Storage**
   - Deprecate custom SHA-256 hashes stored in Firestore user documents once all legacy users migrate to native Firebase Auth credentials.
   - Introduce support for real institutional domains (`@college.edu`) alongside roll numbers for automated self-service password resets.

### Root Cause Analysis

#### 1. Why "Update Password" still requires / uses the present password
In [src/components/ProfileView.tsx](file:///c:/Users/lenovo_samxiao/Downloads/better-cse-aiml/better-cse-aiml/src/components/ProfileView.tsx#L194-L215):
```typescript
if (newPassword.trim()) {
  if (auth.currentUser) {
    await updatePassword(auth.currentUser, newPassword.trim());
  }
}
await updateUserProfile(user.uid, updates);
```
- **The Bug:** `updateUserProfile(user.uid, updates)` only saves profile fields (`name`, `email`, `phone`, `profile_pic`). **It never hashes or saves the new password into the Firestore user document** (`updates.password`).
- **The Consequence:** If the user logs in via roll number and falls into the Firestore fallback in [src/components/LoginView.tsx](file:///c:/Users/lenovo_samxiao/Downloads/better-cse-aiml/better-cse-aiml/src/components/LoginView.tsx#L209-L215), the system checks against `foundProfile.password`. Because Firestore still holds the old password/preset hash, the user is forced to keep using the old password, or Firebase Auth and Firestore become desynchronized.
- Furthermore, Firebase Auth requires `auth/requires-recent-login` if the user's session is older than a few minutes, causing silent failures or alert errors.

#### 2. Why "Reset Password" is missing or broken
- In [src/components/AdminPanelView.tsx](file:///c:/Users/lenovo_samxiao/Downloads/better-cse-aiml/better-cse-aiml/src/components/AdminPanelView.tsx#L1040-L1054), `handleResetPassword` only writes `${roll}_RESET` to Firestore (`updateUserProfile(uid, { password: hashedTempPwd })`). It **does not update Firebase Auth** because client-side admin apps cannot change another user's Firebase Auth password without backend Admin SDK privileges.
- There is **no self-service "Forgot / Reset Password" option** on the [LoginView.tsx](file:///c:/Users/lenovo_samxiao/Downloads/better-cse-aiml/better-cse-aiml/src/components/LoginView.tsx) screen for students because student emails are synthetic (`{roll}.{tenantId}@notx.com`), meaning standard Firebase `sendPasswordResetEmail` cannot reach a real inbox unless an admin or secondary mechanism is provided.

React Router can switch between these without doing a traditional full-page browser reload.

### Why this is better than your current giant page

Your discovery report shows that `App.tsx` is currently acting as the **master application state + view orchestrator**, including global listeners and many views. 

If everything remains inside one giant `App.tsx`:

```text
App.tsx
 ├── Dashboard
 ├── Events
 ├── Users
 ├── Attendance
 ├── Certificates
 ├── Gallery
 ├── Admin
 ├── Support
 └── ...
```

it becomes harder to:

* load only the data needed by the current screen
* protect individual sections
* manage permissions
* maintain code
* test features
* lazy-load heavy modules
* avoid unnecessary renders

### Instead

Have a small application shell:

```text
App
│
├── AuthProvider
│
└── Router
      │
      └── TenantLayout
            │
            ├── Sidebar
            ├── Header
            │
            └── Outlet
                  │
                  ├── EventsPage
                  ├── UsersPage
                  ├── AttendancePage
                  └── ...
```

Then each page owns its feature data.

For example:

```text
/:tenantId/users
        ↓
UsersPage
        ↓
userService
        ↓
Firestore
        ↓
where("tenantId", "==", tenantId)
        ↓
paginated users
```

Instead of:

```text
App starts
   ↓
download every user
   ↓
store every user
   ↓
Users page filters them
```
